## 3. 파일 구조

- `src/App.js`: 화면 연결, 관리자 공통 처리, 실패/저장중 표시, 이동 경고, 종료 원본 조회, 샘플 출고, 자동 외부 동기화 제거.
- `src/mesSafetyCore.mjs`: 정수/양수/수축률/날짜 검사, 최신값 비교, 위치 합계, 라벨 조건 지문, 감사 기록 값 인코딩.
- `src/mesDatabase.mjs`: Firestore와 메모리 대역, 묶음 저장 래퍼, 변경 전후 이력, 삭제 원본 보관, 진행 중 저장 수 추적.
- `src/mesOperations.mjs`: 공정 이동, 성형 분할, 열처리, 수축률 확정, 건조, 관리자 보정/취소, 출고, 입고, 생산지시, 포장 처리.
- `src/mesRuntime.mjs` / `src/mesModePolicy.mjs`: 기본 가상 모드, 운영 주소·설정 검사, 실제 쓰기 명시적 제한, Emulator 연결.
- `src/mesDemoData.mjs`: 실제 LOT와 무관한 합성 시험 자료.
- `tests/safety.test.mjs`: 외부 패키지 없이 Node에서 실행하는 가상 저장소/업무 로직 검사.
- `tests/emulator/`: Firebase SDK와 Auth/Firestore Emulator 통합 검사 구성. 이번 환경에서 미실행.
- `tools/render-smoke.mjs`: React를 간단한 대역으로 바꿔 화면 함수 구성과 대시보드 클릭 참조를 검사. 실제 React 렌더러가 아님.

## 4. 저장 방식과 중요한 구분

새 저장 경로는 최신 원본 읽기 → 조건 검사 → 변경 내용과 감사 기록 준비 → 같은 트랜잭션으로 저장합니다. Firebase 트랜잭션의 읽기 우선, 재시도 가능성, 원자적 저장 제약을 고려했습니다. 트랜잭션 콜백 안에서 실제 인쇄/외부 시트 전송은 하지 않습니다.

### 종료 원본과 재고

현재 WIP에서 취소·분할·전량 출고로 빠진 문서는 같은 ID의 `wipArchive`로 원본을 보관합니다. 이 종료 문서를 재고 합계에 넣지 않습니다. 같은 ID가 다시 생성되는 것을 래퍼에서 막습니다. `parentWipIds`와 `successorWipIds`로 분할 관계를 남깁니다. 취소는 원재료 자동 반환과 같은 뜻이 아니며 이미 소비한 원료를 임의로 늘리지 않습니다.

### 감사 기록

`mesAudit`에 사유·담당자·변경 전후를, `mesControl/main`에 최신 수정 번호를 저장합니다. 수량과 이력 중 하나만 저장되는 상태를 피하도록 같은 작업으로 묶습니다. 감사 목록은 최근 50개만 구독합니다. Firestore serverTimestamp 같은 변환값은 감사 기록 배열에 그대로 넣지 않고 형식 태그로 인코딩합니다. 같은 저장의 서버 시각은 감사 문서의 `createdAt`을 참조합니다.

이 감사 기록은 전체 데이터베이스 백업/복구 체계가 아닙니다. 원본과 결과를 한 문서에 보관하므로 큰 장비 문서는 제한에 걸릴 수 있습니다. 방어적으로 변경 데이터 약 700KB 또는 180개 쓰기 요청을 넘으면 실패시키지만, 실제 Rules 접근 횟수·인덱스 크기·쓰기 지연 한도까지 이 환경에서 검증하지는 못했습니다.

### 오래된 프로그램과 서버 권한

`mesControl`을 함께 갱신하는 수정 클라이언트 사이에서는 목록 조회와 저장을 순서화합니다. **구버전이나 직접 Firebase 접근처럼 이 절차를 쓰지 않는 작성자는 보호 범위 밖입니다.** 최종 운영에서는 보안규칙 또는 서버 쓰기 API가 새 검사·권한을 강제해야 합니다. 화면 PIN과 클라이언트 `isAdmin`만으로 권한이 보장되는 것은 아닙니다.

현재 ZIP에는 운영 Firestore Rules, IAM, 관리자 사용자 목록, BarTender 작업자, Apps Script의 서버 코드가 없습니다. 이를 추정해 운영 규칙으로 교체하지 않았습니다.

## 6. 기술 담당자용 실행 방법

일반 가상 로직 검사는 Node만 있으면 실행됩니다.

```sh
npm run safety:test
```

실제 UI 빌드는 네트워크가 되는 환경에서 원래 저장소의 의존성을 설치하여 확인해야 합니다. 원본의 `firebase`, `lucide-react` 등 `latest` 지정은 임의 버전으로 교체하지 않았습니다. 최초 정상 설치 후에는 실제 사용된 버전을 잠그고 lockfile을 추가해야 재현성이 생깁니다.

Emulator 검사는 설치된 Firebase CLI, Firebase SDK 의존성, Java 환경이 필요합니다.

```sh
npm run safety:emulator
```

이 명령은 `tests/emulator` 안에서 **demo-dasan-mes** 프로젝트만 사용합니다. 스크립트는 Firestore/Auth Emulator 주소가 지정한 loopback 주소와 다르면 실행을 거부합니다. 시험용 Rules는 인증을 요구하고 `denied` 경로를 일부러 막아 권한 거부 시 부분 저장이 없는지 검사합니다. **운영 규칙이 아닙니다. 절대 firebase deploy로 올리지 마세요.**

화면 함수 대역 검사는 로컬 TypeScript가 있을 때만 `npm run safety:render-smoke`로 실행합니다. `MES_TYPESCRIPT_PATH`로 별도 설치 위치를 지정할 수 있습니다. 운영 앱이 그 도구를 import하지는 않습니다.

## 7. 운영 모드와 적용 보류 조건

기본은 `demo`입니다. `emulator`는 localhost만 허용하며 demo 프로젝트를 사용합니다. `production`은 명시적으로 선택하더라도 정확한 허용 호스트, Firebase 설정, 확인된 projectId가 없으면 연결을 열지 않습니다. 쓰기는 별도 승인 플래그가 참이어야 하며 Google Sheets 전송도 별도 설정입니다. 현재 사용자는 이 값들을 설정하지 말고 가상 Preview만 확인해야 합니다.

운영 전에는 최소한 다음 승인이 필요합니다.

1. Vercel 빌드와 실제 태블릿 주요 공정·관리자 동작 합격.
2. Firebase Emulator 통합 검사와 실제 운영 보안규칙/권한 검토 합격.
3. 기존 열려 있는 태블릿·관리자 페이지·구 Preview 등 구버전 쓰기 경로 차단. 단순 안내만으로 보장할 수 없음.
4. 정식 백업 및 되돌리기 계획. 운영 화면 되돌리기는 이미 바뀐 데이터까지 되돌리지 않음.
5. 인쇄 요청과 실제 출력·라벨 회수 확인, 샘플/일반 출고 담당 절차 확정.
6. 667처럼 원기록이 없는 로트, 886의 잔존 슬롯 등 기존 불일치는 별도 승인된 보정으로 처리. 이 릴리스에서 자동 수정하지 않음.

라벨 요청 성공은 인쇄 성공이 아닙니다. RC1은 실제 라벨을 확인했다고 사용자가 확인해야 포장을 마치게 하지만, 외부 프린터 작업자가 요청을 중복 처리하는 문제까지 해결하지는 못합니다. 기존 GTIN·SKU 매핑의 규제 적합성도 이 검사의 범위가 아닙니다.
