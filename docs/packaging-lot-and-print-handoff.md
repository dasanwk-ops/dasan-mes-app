# 포장·라벨 로트 변경 및 현장 인쇄 연결 인계

## 확정 규칙

- 변경 대상은 기존 `F…` 포장·완제품·라벨·출고 로트(`packLot`)입니다.
- 새 번호: `[제조일 YYMMDD][높이 T]US5[순번 2자리]`.
- 날짜는 기존 라벨의 제조일 판정과 동일한 실제 열처리 완료일입니다. 출력일이나 포장일로 대체하지 않습니다.
- `US`는 shade disc 구분, `5`는 공장번호이며 둘 다 고정입니다.
- 동일 제조일은 높이·색상·제품군에 관계없이 순번을 공유합니다. 다른 제조일은 `01`부터 시작합니다.
- 최초 출력 요청이 저장되는 순서로 번호를 확정합니다. 며칠 뒤 출력해도 제조일의 기존 순번을 이어갑니다.
- 새 번호의 최대 순번은 `99`입니다. 초과하거나 카운터가 손상되면 발급을 중단하고 오류를 표시합니다. 번호를 순환하거나 임의로 세 자리로 늘리지 않습니다.
- 내부 MIX 번호는 원재료·공정 추적 연결로 보존합니다. 내부 `-A/-B` 분리 표시는 추적용이며 새 포장·라벨 번호에는 붙지 않습니다. 분리된 최종 로트마다 새 순번을 발급합니다.

| 제조일 | 높이 | 최초 출력 순서 | 포장·라벨 로트 |
|---|---|---|---|
| 2026-10-14 | 25T | 해당 제조일 첫 번째 | `26101425TUS501` |
| 2026-10-14 | 30T | 해당 제조일 두 번째 | `26101430TUS502` |
| 2026-10-14 | 25T | 해당 제조일 세 번째 | `26101425TUS503` |
| 2026-10-15 | 30T | 해당 제조일 첫 번째 | `26101530TUS501` |

## 저장 및 기존 기록

제조일을 확인한 최초 라벨 출력 요청에서 WIP의 로트, 해당 제조일 카운터, 출력 대기 문서, 출력 이력을 하나의 Firestore transaction으로 저장합니다. 실패하면 모두 저장되지 않습니다. 동시 발급은 transaction 재시도로 서로 다른 순번을 받습니다.

기존 `F…` 번호가 이미 있는 제품과 기존 출력 대기 문서는 변경하지 않습니다. 새 번호는 아직 포장로트가 없는 제품에 적용합니다. 기존 번호의 재출력·완제품 재고·출고 이력도 유지됩니다. 새 체계는 `systemCounters/packLot-US5-YYMMDD`를 사용하며 기존 F 번호의 카운터와 섞이지 않습니다.

**변경 전에 투입된 공정 중 제품도 최종로트가 없으면 새 체계를 적용합니다.** 투입일이나 변경일을 기준으로 제외하지 않습니다. 기존 원재료·MIX 연결, 생산지시, 수량, 열처리·수축률 기록을 유지한 채 공정을 진행하며 제조일이 확인된 최초 라벨 요청에서 번호를 확정합니다. 기존 WIP 전체를 일괄 재작성하거나 임시 번호를 미리 발급하지 않습니다.

오래된 데이터의 최종번호가 `lot`, `labelPrintedPackLot`, `labelPrintHistory[].lotNumber` 또는 F 번호로 저장된 `mixLot`에만 남아 있어도 그 번호를 보존하고 최초 요청에서 `packLot`에 복원합니다. `MIX-…`는 내부 추적번호이므로 최종번호로 취급하지 않습니다. 서로 다른 기존 번호가 발견되거나 출력 흔적은 있지만 번호를 복원할 수 없으면 새 발급을 중단합니다. 이 경우 원기록과 실제 라벨을 확인하여 처리하며 임의로 순번을 새로 받지 않습니다.

소재 이관·배합·성형·검수 완료·건조 시작/완료는 현재 저장된 공정을 다시 확인합니다. 수량을 배분하거나 차감할 때 화면과 최신 수량이 다르면 중단합니다. 배합은 최신 제품·수량·중량 조건을 확인한 후 원재료를 차감합니다. 정상·불량 수량은 정수로 검증하고 불량은 실제 수량 이내로 제한합니다. 성형 분리는 고유한 문서 ID를 사용하며 모든 자식에 양쪽 정상·불량 배분 기록을 남깁니다. 소재 이관·검수·건조는 필요한 항목만 갱신하여 최신 로트·이력 데이터를 보존합니다. 건조 완료와 해당 로트 입력 정리는 함께 저장하며 다른 로트의 건조 입력을 보존합니다. 관리자 수정·삭제 역시 확인창 이후 공정이나 수량이 바뀌었으면 중단합니다.

배포 후 이미 열어 둔 작업 화면은 새로고침하여 새 처리 방식을 사용합니다.

제조일 기록이 없으면 포장 화면에서 실제 열처리 완료일, 확인 근거, 담당자를 입력해야 합니다. 번호나 포장일로 제조일을 추정하지 않습니다. 입력한 확인 정보는 실제 열처리 이력과 별개로 보관합니다.

이미 출력한 새 로트의 제조일 또는 높이가 바뀌면 재출력을 차단합니다. 기존 번호를 조용히 변경하지 않으며, 원기록·기존 라벨을 확인해야 합니다. 출력 후 제품군/색상이 바뀌어도 이전 출력 조건으로 포장완료할 수 없습니다.

공정으로 되돌린 제품을 여러 로트로 다시 분리하는 경우 자식 로트는 부모의 포장번호와 출력완료 상태를 이어받지 않습니다. 이전 번호·출력 이력은 `packagingLotLineage`에 보관하며, 자식은 각각 새 번호와 라벨이 필요합니다.

## 다른 PC의 프린터 연결 항목

MES 출력 경로는 기존 `print-queue`를 유지합니다. 현장 연동 프로그램은 **문서 ID로 작업을 구분**합니다. 기존 필드는 유지하고 디스크 라벨의 두 줄 표시용 필드만 추가합니다.

| 필드 | 예시 | 연결 용도 |
|---|---|---|
| `lotNumber` | `26101425TUS501` | 전체 LOT. 조회·이력 및 기존 바코드 LOT 입력에 그대로 사용 |
| `lotNumberLine1` | `261014` | 디스크 라벨 LOT 칸의 윗줄 |
| `lotNumberLine2` | `25TUS501` | 디스크 라벨 LOT 칸의 아랫줄 |
| `sourceLot` | `MIX-261010-123-A` | 내부 MIX 추적정보. 라벨 LOT를 대체하지 않음 |
| `mfgDate` | `2026-10-14` | 실제 제조일. 로트 앞 날짜와 일치 |
| `mfgDateSource` | `heat_history` | 제조일 확인 근거 구분 |
| `height` | `25` | 제품 높이 |
| `sku`, `ref` | `Z345BL325`, `Z345BL325D98` | 기존 제품·REF 매핑 |
| `quantity` | `10` | 인쇄 요청 장수 |
| `unitQty` | `1` | 라벨당 제품 수량 |
| `shrinkage`, `scaleFactor` | `19.5`, `1.2422` | 기존 수축률·확대율 |
| `status` | `pending` | 기존 출력 대기 상태 |

일반적인 두 자리 높이의 새 번호는 13자입니다. F로 시작하는 번호만 허용하는 검사, 기존 글자 수 고정, 숫자 변환, 문자열 잘라내기가 있다면 수정해야 합니다. 제조일은 `mfgDate`, LOT는 `lotNumber`로 따로 연결합니다. 프린터 PC에서 일련번호를 다시 계산하거나 디스크마다 증가시키지 않습니다. 동일 요청의 모든 라벨은 같은 LOT를 사용합니다.

디스크 라벨의 LOT 칸은 가운데 정렬한 텍스트 두 개로 연결합니다. 위 텍스트에 `lotNumberLine1`, 아래 텍스트에 `lotNumberLine2`를 넣으면 `261014` / `25TUS501`로 표시됩니다. 두 값은 최초 번호 확정 후 생성하며 재출력 때도 같은 전체 번호에서 생성합니다. MES 출력 요청 미리보기에도 이 배치를 표시합니다. 실제 글꼴·크기·간격은 현장 라벨 폭에 맞춰 서식에서 조정합니다.

줄바꿈은 사람이 읽는 디스크 라벨 표시에만 적용합니다. `packLot`, `lotNumber`, 출력 이력, 출고 데이터, 바코드에 전달하는 전체 LOT에는 줄바꿈이나 공백을 삽입하지 않습니다. 기존 F 번호는 윗줄에 전체 번호를 표시하고 아랫줄은 비웁니다. 변경 전에 생성된 대기 요청에 두 필드가 없으면 현장 연결 프로그램에서 전체 `lotNumber`가 새 형식인 경우에만 앞 6자리/나머지로 나누고, 다른 형식은 그대로 한 줄 표시합니다. 이전 대기 문서는 일괄 재작성하지 않습니다.

실제 BarTender 서식(.btw), 프린터 PC 프로그램, 바코드 데이터 매핑은 이번 작업 범위 밖이며 현장에서 후속 연결합니다. GTIN과 UDI의 AI 항목을 이번 변경으로 새로 결정하거나 변경하지 않습니다. `sourceLot`를 개별 제품 시리얼로 해석하지 않습니다.

현장 연결 시 비운영 테스트 작업으로 다음을 확인합니다.

1. 윗줄 `261014`, 아랫줄 `25TUS501`이 가운데 정렬되고 잘리지 않는지 확인. 두 줄을 이어 붙인 값이 전체 `lotNumber`와 일치하는지 확인.
2. 제조일 `2026-10-14`가 별도 날짜 필드에 정확히 출력되는지 확인.
3. 같은 로트 여러 장 및 재출력 시 모든 라벨의 LOT가 같은지 확인.
4. 분리 로트는 다른 순번, 다른 높이도 같은 제조일이면 이어지는 순번인지 확인.
5. 기존 F 번호 라벨의 재출력도 가능한지 확인.
6. 확정된 바코드 서식으로 시험 인쇄 후 스캐너 판독값을 MES 필드와 비교. LOT 입력에는 줄바꿈이 없는 전체 번호가 사용되는지 확인.

## 검증

- `npm run test:packaging-lot`: 형식, 제조일/높이 혼합, 동시 발급, 중복 요청, 재출력, 기존 F 번호, 실패 시 원자성, 제조일 미확인, 최대 순번, 분리 이력, 포장완료, 제조일 변경 차단.
- `npm run test:finished-goods`: 기존 완제품 재고·이력·수량 정정.
- `npm run test:wip-lot-safety`: 기존 공정품의 이력 보존, 오래된 화면·중복 완료·삭제된 대상 차단, 동시 성형 분리, 불량 수량 검증, 건조 데이터 동시 편집, 저장 실패 시 전체 취소.
- `node tools/test-heat-completion.cjs`: 기존 열처리 흐름.
- `npm run build`: 기존 빌드 단계까지 통합 검증.

테스트는 가상 데이터로 실행합니다. 실제 출력 대기열에 시험 작업을 넣거나 프린터를 작동시키지 않습니다.
